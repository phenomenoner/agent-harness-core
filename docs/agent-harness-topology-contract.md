# Agent Harness Topology Contract

Date: 2026-07-26

This contract turns the architecture handoff into release-gate input. Use it before changing channel ingress, channel state, prompt assembly, runtime queueing, Codex execution, final outbox, delivery, progress, workers, cron, or memory. The operations handbook remains the live operational source of truth; this file is the compact dependency map and scenario matrix that reviewers and external coding agents should apply to code changes.

## Source And Deployment Boundary

The source checkout and the nested live deployment are separate authority roots even when they share a parent directory. Source code, public documentation, tests, and Cargo build output belong to the checkout. Live config, state, agent workspace, execution workspace, deployed tools, rollback generations, and cutover evidence belong below `.agent-harness/`.

| Role | Canonical relative path | Contract |
|---|---|---|
| live CLI | `.agent-harness/bin/current/agent-harness.exe` | The only executable path used by live supervisors and loop children. |
| immutable release copy | `.agent-harness/bin/releases/<release>/agent-harness.exe` | Hash-addressed or release-labelled candidate retained for provenance. |
| agent source workspace | `.agent-harness/workspace/` | Prompt, rule, skill, and durable agent-document authority. |
| default execution cwd | `.agent-harness/runtime-workspace/default/` | Ordinary live Codex cwd; not a source checkout. |
| deployed dependencies | `.agent-harness/tools/` and `.agent-harness/scripts/` | Exact gateway, Codex CLI, and bridge dependencies used by live commands. |
| hot rollback | `.agent-harness/rollback/hot/<generation>/` | Complete, verified generations; retain the newest three. |
| cutover evidence | `.agent-harness/evidence/cutovers/<generation>/` | Sanitized path, hash, gate, and post-readback evidence. |
| source build output | `target/` | Rebuildable source/staging output. Every explicit Cargo target directory remains below the resolved source root; build, release, worktree, cache, and evidence paths must not escape into its parent. Never the canonical live executable or rollback store. |

Every cutover must fail closed if a desired supervisor or child resolves its executable, runtime workspace, gateway script, Codex CLI, bridge command, rollback bundle, or evidence directory to the source checkout. An explicitly scoped source-development turn may select the source checkout as its execution cwd, but that exception must be supplied per task and must not rewrite the default live supervisor topology.

## Identity Axes

Every channel-origin turn is keyed by these axes. A change that drops, normalizes, or compares only a subset of them can create cross-agent or cross-session regressions.

| Axis | Meaning | Must Be Preserved Through |
|---|---|---|
| `platform` | Telegram, Discord, or another channel adapter. | ingress, queue, progress, outbox, delivery receipts, trace |
| `accountId` | Provider account or bot identity when configured. | channel identity, outbox, delivery, receipts |
| `channelId` | DM/chat/channel/thread address. | channel state, queue item, delivery intent, trace |
| `userId` | Sender identity inside the channel. | permission gate, channel state, session key, trace |
| `agentId` | Runtime owner, not just persona text. | provider/model defaults, Codex home, prompt files, memory namespace, runtime lane, session freshness, outbox, delivery, OperationPlan scope |
| `sessionKey` | Conversation/session continuity key. | command state, runtime queue, Codex plan, transcript, freshness guard, prompt/memory task boundary |
| `virtualSessionId` | Stable task-continuity owner across concrete-session rollover. | working-context resolver, prompt manifest, operation plan, child result owner, coordinator resume |
| `runtimeClass` | Interactive, cron, worker, maintenance, or another runtime lane. | queue selection, lease, retry/dead-letter policy, status |
| `sourceQueueId` | Correlation for one queued turn. | Codex completion, final outbox, delivery receipts, trace |
| `backendContextGeneration` | Opaque Codex/backend context generation, not a routing wildcard. | prompt manifest, injection ledger, reinjection decision, prepared execution receipt |

Two digests serve different boundaries. The full concrete-lane identity includes `sessionKey` and `backendContextGeneration`; it must change across concrete rollover. The virtual exact-lane digest retains platform/account/channel/user/agent/runtime/root-virtual-session axes but deliberately excludes the concrete backend generation, so one `virtualSessionId` can own a frozen skill manifest across rollover without becoming a cross-lane wildcard.

Runtime ownership and runtime capacity are separate contracts. One execution lease is bound to the exact account-aware agent/channel/user/session lane. `runtimeClass` supplies global and class capacity policy only; its file lock protects the bounded read-modify-write of lease metadata and must be released before prompt, skill, context, or backend preparation. Every fresh or prepared-resume branch arms exact-class unwind immediately after durable lease persistence, so a later resume, receipt, log, prompt, or filesystem failure releases only that exact acquisition before returning. Release compares the complete owner envelope, including `acquiredAtMs`; a late unwind from owner A cannot remove successor B for the same queue ID. A busy class lock is retryable backpressure, never operator cancellation, `Stopped.`, or a terminal source closure. Distinct exact lanes may prepare and run concurrently when configured capacity permits.

The v1 run-once `needs-user` status and terminal disposition remain a rollback-compatible carrier for both concrete Goal response requirements and visible Goal parks. They are not sufficient presentation authority by themselves. Consumers must join `sourceClosureKind` and `sourceClosureReason`: observe/policy denial and Goal pause/blocked render as `goal-parked`; typed Goal input, authority, or authentication render as the corresponding Goal response requirement; only a connector approval without a Goal or parked source closure may render `WaitingForApproval`. A future schema revision may split the carrier, but this release does not write an enum value that an older rollback binary cannot deserialize.

Queue-backed Windows app-server children add a second exact-lane ownership boundary. Before any process exists, `codex_runtime` persists `agent-harness.runtime-queue-child-cleanup-fence.v1` with the queue, runtime class, canonical lane digest, lease-owner digest, and exact acquisition. The root is created suspended with a preconfigured kill-on-close Job in its `STARTUPINFOEXW` Job list, then the fence is compare-and-bound to the root PID and OS start generation before resume. Scope exit terminates the Job, bounded-waits the root, releases its process/thread handles, and reads back `ActiveProcesses == 0` before recording monotonic cleanup proof and compare-removing the fence. Proof-write and clear failures retry boundedly under the same process. Failure to prove Job termination, exact-root exit, or `ActiveProcesses == 0`, persistent cleanup-proof retry exhaustion, and an unavailable retry mechanism each write fatal-generation evidence and terminate that runtime generation so a supervised restart can use exact dead-generation evidence. Expiry, terminal reaping, and a same-lane successor remain blocked while a fence exists. Unknown, malformed, live, non-OS-proven, or authority-mismatched evidence remains fail-closed; stale authority never clears a successor. This hard process-tree containment contract is currently Windows-only. Other operating systems retain their existing bounded child cleanup but do not claim atomic tree containment from this schema.

## Supervisor Process Shapes

The supported Windows topology has one functional control-plane owner:

```text
Windows Task Scheduler
└─ hash-bound hidden launch adapter
   └─ agent-harness supervisor-master
      ├─ runtime-loop
      ├─ worker-loop
      └─ ... one directly owned child per configured service
```

The adapter has no topology, restart, routing, or service-state authority. It verifies the plan and binary, starts the Rust master with no console window, waits synchronously, and returns the master exit code to Task Scheduler. The same master engine can sit below another thin native host adapter when that adapter has equivalent lifecycle evidence.

`supervisor-master --mode direct-owner` acquires the exclusive form of the deployment ownership lease, enters a kill-on-close Windows Job before spawning, and directly retains each configured service handle. The master is the only canonical service-state writer. It owns exact master and child-attempt generations, freshness-bounded heartbeats, restart/backoff/breaker decisions, bounded drain, and generation-scoped ephemeral stop markers. A directly owned Rust wrapper remains the canonical heartbeat identity even when it launches a data-plane subprocess; that subprocess must not overwrite the wrapper heartbeat. A wrapper with descendants also arms a nested kill-on-wrapper-exit boundary, so a per-service timeout or restart cannot leave grandchildren alive inside the master's broader Job.

The compatibility topology remains available for migration and rollback:

```text
thin OS host adapter
└─ supervisor-reconcile keeper
   ├─ detached supervisor-run(runtime) ── runtime-loop
   ├─ detached supervisor-run(worker)  ── worker-loop
   └─ ... one supervisor-run plus child per configured service
```

Compatibility reconcile and `supervisor-run` processes hold shared lease handles, so either compatibility owners or one direct master may exist, never both. In compatibility mode, each `supervisor-run` state envelope records its PID plus exact OS process-start identity independently of the current child attempt. A dead child or `restart-backoff` state remains unhealthy and observable, but it must not cause reconcile to create another owner while that exact managed supervisor is alive. PID-only evidence, a mismatched start identity, and observe-only state cannot fence recovery.

Migration between ownership modes remains stopped-state only. After a direct-owner master crash, a replacement master may recover a known non-stopped record only after it acquires the exclusive ownership lease, the record carries exact prior master and applicable child process-start identities, and every recorded process is positively dead. A draining child whose identity has already been cleared is recoverable only when the canonical record also carries its positive exit time and exit code; a missing child identity without that durable exit proof remains blocked. Recovery never adopts a PID and writes a generation-specific import receipt bound to the executable, config, service specification, and imported source digests. A config-generation change is checked before every direct initial or restart spawn and drains the master; desired arguments or environment cannot replace authoritative deployment, service, executable, ownership, or generation values.

Linux implements native `/proc` process liveness/start-generation identity and shared/exclusive Unix ownership leases, so observe and import logic can fail closed without treating every PID as unknown. Direct ownership remains Windows-only because equivalent Unix process-group/session containment, signal drain/escalation, and native host recovery are not implemented. Unsupported hosts reject direct-owner mode before lease, receipt, process, or canonical-state mutation. macOS does not yet have equivalent lifecycle evidence.

Provider gateways remain data-plane children; a Discord or Telegram gateway must not become the control-plane master. A guarded Windows cutover validated the thin-adapter, one-master, nine-direct-child shape, restart and health readback, rollback readiness, and exact-lane Telegram and Discord delivery. That is Windows cutover and provider-smoke evidence, not promotion of an exact tagged artifact, cross-platform parity, or a long-duration endurance claim.

Every non-interactive Windows child launch defaults to no-console or hidden-window semantics. Rust subprocesses use the shared `CREATE_NO_WINDOW` policy, Node uses `windowsHide`, generated PowerShell uses hidden window style, and the root Task Scheduler action uses the hash-bound launch adapter. The detached reconcile-parent boundary retains `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` instead because `CREATE_NO_WINDOW` is not a substitute for that control-domain isolation. Operator-interactive authentication and the console/control-break integration test are explicit exceptions. Stdio redirection and Task Scheduler's task-list `Hidden` setting are not evidence that a console window cannot appear.

## Mandatory Impact Matrix

Codex backend provenance is a deployment boundary. Candidate and live supervisors must resolve one deployment-owned canonical executable, never PATH or global npm, and must fail closed unless an `agent-harness.codex-backend-provenance.v1` receipt proves exact version `0.144.5`, executable SHA-256, npm/native package integrity, provider-scoped `CODEX_HOME`, config digest, and correlated parent/child lifecycle. Source and staging may prepare this receipt; live mutation still requires explicit operator cutover approval.

Backend authentication is a provider and operator boundary. Every provider resolves a canonical harness-owned `CODEX_HOME`; a newly created home is Unix `0700` or a protected current-operator-only Windows DACL, while existing-home ACL migration requires stopped-state approval. An empty home is explicitly unauthenticated and never falls back to a user-global Codex home. Only the interactive `backend-auth` operator command may run browser, device-code, API-key-stdin, cancel, refresh, or logout flows. Durable state and ordinary Telegram/Discord turns may carry only secret-free lifecycle/readiness/correlation evidence. Raw operation/login ids are reduced to one-way digests, and runtime-ready requires same-generation `account/read` plus `model/list` evidence linked to the canonical executable provenance receipt. With the default-off runtime gate enabled, a turn without ready evidence becomes nonterminal `auth-deferred`: it is non-claimable, consumes no retry budget, produces no final/error outbox, and is not given credentials or silently routed through another provider home. Only a strictly newer ready generation may append its deterministic exactly-once `retry-pending` wake; append-before-mark ordering makes restart reconciliation lossless.

Web search is a provider capability and exact-lane tool-authority boundary. The runtime reads `modelProvider/capabilities/read` on the same app-server connection, sends an explicit top-level `web_search` on thread start/resume, and never derives the mode from sandbox/full-access state. Cached is the ordinary default; live requires explicit freshness intent plus allowed lane policy; sensitive, offline, replay, missing-capability, or denied lanes are disabled. A thread may resume only when its receipted effective mode/provider/lane binding still matches. Search items remain untrusted turn context: durable action receipts hash query text, omit private URLs, and cannot themselves authorize memory, skill-learning, dream, command, or delivery effects.

## Agent-Boundary Scenario Pack

Run or add tests equivalent to these scenarios for channel/runtime/session changes:

1. Same agent, same channel/user, old session completes after `/new`: final reply is suppressed and an explicit stale-session warning is recorded.
2. Different agents, same platform/channel/user, one agent has an active session in shared channel state: the other agent's completed turn is not suppressed solely because the shared state belongs to a different `agentId`.
3. Non-main agent normal message reaches prompt assembly with that `agentId`, its own workspace/prompt files, provider/model defaults, Codex home, and memory namespace.
4. Completed turn produces exactly one source-correlated final outbox record or one terminal error/dead-letter notification.
5. `trace --queue-id <id>` reconstructs ingress, queue id, Codex completion, final outbox, and delivery or terminal notification; legacy `--id` remains compatible, and supplying both selectors fails closed.
6. Fresh request after `/new` uses the new concrete session as a task boundary: previous-task imported memory context is not injected unless a later policy explicitly opts in.
7. `/think max` and `/reasoning max` are command-only aliases over one agent-scoped state; the next normal turn carries exact `max`, while a sibling agent sharing platform/account/channel/user does not inherit it. Exact `ultra` is rejected and `ultra-high` remains the legacy `xhigh` alias.
8. Prompt manifest and injection ledger bind to the exact full lane plus backend context generation. A sibling agent or different lane cannot reuse another agent's injected configuration, and a changed/deleted config file or changed backend generation produces the expected bounded reinjection/tombstone behavior.
9. Sibling children may use different immutable provider/model/effort policies. Retry cannot silently change a child's policy, and every expected terminal child contributes either a bounded/redacted result with opaque pointers or an explicit failed-omission envelope to the exact parent owner.
10. Child/external-agent progress, completion, and error are internal evidence. The exact master coordinator consumes only validated envelope fields and structural metadata, waits until the whole exact lane is idle, schedules one idempotent continuation, and is the only participant allowed to emit parent user-facing output.
11. Skill shadow routing alone writes one privacy-safe exact-lane route receipt and no manifest, delivery, usage, learning, or proposal state; virtual-manifest observation is separately enabled and still leaves active selection and prompt bytes identical.
12. A concrete backend rollover rehydrates the frozen virtual-session skill revision without a fresh route link or positive-use event; `/new` closes the old manifest and begins with no inherited task intent or active skill state.
13. Runtime completion records ordinary model final as unknown until external verification, joins delivery/outcome/episode under the same virtual session, emits one retry-idempotent terminal review, and produces only a reversible unapplied improvement proposal.
14. An ordinary final that needs more than 16 semantic presentation blocks is durably retained as canonical text without a lossy automatic presentation. A persisted legacy 16-block projection falls back before the first rich unit; Discord and Telegram deliver all ordered chunk bodies, failed required chunks report `fullTextPreserved=false`, and a terminal receipt suppresses restart replay.
15. A parent turn interleaved with child or foreign thread/item completion accepts only the exact owned parent final in both streamed and stdout-recovery paths; rejected events remain diagnostic and cannot close the parent.
16. `/new` with an active backend goal records the frozen old-session closure intent and cancel fence before mutation, holds ordinary messages without starting a model turn, then activates exactly one frozen replacement and replays held messages FIFO after authoritative closure. Ambiguous closure leaves the old session current.
17. Historical governed closure resumes the original thread, records terminal projection and lineage evidence in order, never borrows a fresh channel turn's final ownership, and is idempotent across restart and duplicate caller effects.
18. A connector approval prompt renders two non-secret public actions. 19. A required source final holds terminal progress until the exact source queue and lane has terminal delivery evidence. Another queue/lane cannot release it; explicit typed non-delivery and canonical campaign-final reuse remain auditable alternatives.
20. A source-owned turn with a nonterminal goal resolves through one typed source closure. Exact-lane active policy commits one child before suppressing the parent; observe, disabled, and non-admitted lanes append one visible park, retain no lease, remain FIFO-nonblocking across restart, and cannot become logical success. Review-only, child, stale-session, or wrong-owner evidence remains internal.

The class metadata lock is not held across preparation; transient capture contention becomes retryable backpressure and never a terminal `Stopped.` delivery. Injected failure after durable acquisition on fresh, requested-prepared-resume, and automatic-prepared-resume paths releases the exact acquisition, while stale prepare and pipeline release guards preserve a substituted successor lease for the same queue ID.
22. A demonstrably active current-owned Goal may adopt its same-thread native continuation under the same exact lease. A terminal, blocked, paused, or explicitly parked Goal closes the provider process, releases that lane, and cannot be auto-woken; unrelated lanes remain independently runnable.
23. `/new` survives handler failure and both sides of its durable intent boundary. A handler that unwinds before any transition marks its claim retryable even if the gateway process remains alive; a dead process is taken over only with PID plus process-start proof. Once the transition intent exists, ingress retry cannot create another target; transition reconciliation appends the same deterministic acknowledgement after intent, state, or acknowledgement crash windows.
24. Status and health derive outbox counts from the same cursor-backed delivery index as delivery planning. A terminal receipt outside a bounded tail window cannot resurrect an old row as pending or make readiness false.

## Support-Plane Knowledge Graphs

The topology contract is canonical text. Generated graph tools are support-plane aids: they help reviewers discover relationships, but they do not replace source code, tests, release gates, or openclaw-mem Store/Pack/Observe ownership.

Understand-Anything is a good fit for codebase topology exploration because it can generate `.understand-anything/knowledge-graph.json` with file/function/class/dependency nodes, architecture layers, guided tours, semantic search, and diff-impact views. Use it for these bounded jobs:

- Build or refresh a repo-local code topology graph after behavior-changing architecture work.
- Ask code-graph questions such as "which modules touch session freshness?" or "what changes affect final outbox delivery?"
- Compare the generated graph against this contract to find missing component edges or stale docs.
- Produce reviewer-facing navigation aids for large changes before release review.

Do not use it for these jobs:

- Do not treat generated graph output as the canonical memory store.
- Do not let it write live harness state, secrets, channel ledgers, or `.agent-harness` private data into tracked documents.
- Do not enable auto-update or dashboard launch as a release gate until the graph artifacts, ignore policy, and public hygiene behavior are verified.
- Do not merge generated graph facts into openclaw-mem as trusted facts without provenance, freshness, and human-readable source file pointers.

Recommended staged adoption:

1. Create `.understand-anything/.understandignore` that excludes `.agent-harness/`, `.debug/`, `.tmp/`, `target/`, `.public-export/`, secrets, generated images, and large ledgers.

4. Record a compact memory/graph freshness receipt that links the graph commit hash, topology contract version, and source docs used for generation.
5. Use the graph to support impact review, while keeping `docs/agent-harness-topology-contract.md`, `docs/invariants.md`, and tests as the release gates.

The generated page embeds `docs/topology-explorer-data.json` so it can be opened directly from disk. It may help operators browse components, identity axes, release gates, and open gaps, but it is still a support-plane artifact; do not edit the HTML/JSON by hand or treat it as canon.

### Progress Ordering Binding

- `progress-delivery-volume-gap`: progress delivery preemption is queue-local. A global wake from another lane must not drop the whole pending batch, first-surface sends are not preempted before any provider message exists, and same-queue providerless orphan surface claims are reclaimed without waiting for the claim TTL.
- `runtime-terminal-control-gap`: progress delivery must consume durable terminal-control evidence before rendering non-terminal cached progress. Terminal-controlled queues may emit one terminal close edit for existing provider surfaces, record `progressSuppressedReason=terminal-control-present`, drop cached ghost events only after the close receipt is recorded, and then stay silent. Normal terminal progress paths keep their compacted terminal context so late events and retryable lane failures do not suppress legitimate retries.

### Progress Source-Authority Binding

- A last-committed or unavailable progress index snapshot is diagnostic evidence only. It must not create, edit, or replay provider-visible progress from `compactedEvents`; the bounded cache is retained until a fresh source projection can rebuild the plan.
- A fresh projection may contain retained history after a reset or migration. If a queue has no existing provider surface and its latest event is older than the progress freshness window, it is suppressed rather than creating a late `Send`; an existing provider surface may still converge through its normal edit/terminal path.
- `progress-delivery-loop` owns a watched stop file. It must check before provider I/O and release every unattempted fresh-send claim when stopping, so restart/cutover cannot strand a short-lived claim or require a broad process kill.

### Controlled Coordinator Replay Binding

- A provider-visible coordinator replay is an operator-only verification surface, not a general subagent import or recovery command. It must require an explicit bounded source marker, exact full-lane identity for `main`, its currently active exact channel session when v2 state exists, authoritative catalog admission for that lane and every planned child execution agent, exactly two distinct child models with at least one exact `max`, and a separate explicit confirmation.
- The command must use the existing V5 transactional child/wait/watchdog path. It must not create child work through direct database edits, generic historical-ledger selection, or an untyped runtime queue append.
- Child turns remain worker-origin internal work. The only provider-visible final is the exact master continuation after the mailbox and durable coordinator contract completes; failure evidence is retained privately and never retried by a scheduled self-check.

## Skill Ecosystem V2 Ownership And Activation

Skill serving and skill learning use three explicit lifetimes. A concrete `sessionKey + backendGeneration` owns prompt delivery and cache/rehydration state only. An exact-lane `virtualSessionId` owns bounded task intent, the frozen catalog/topology/skill revision manifest, attributable outcomes, and one terminal learning review. The agent library identified by `agentId + libraryRevision` owns canonical packages, topology, statistics, proposals, dream runs, and later activation epochs.

The joined evidence chain is `skill-routing.v2 -> skill-delivery.v2 -> skill-outcome.v1 -> virtual-session episode -> knowledge-classification.v1 -> skill-learning.v2 -> skill-dream-run.v1 -> catalog/topology activation`. Every link retains the same agent, root-session hash, exact-lane digest, and virtual-session ID. A concrete-session rollover may emit `deliveryReason=rehydration` for a frozen skill body, but it creates no fresh routing, use, outcome, or improvement event. `/new` terminalizes the old manifest and starts with no inherited task intent or active skill entry.

Shadow routing runs only after runtime preparation has the exact account-aware full lane. Its query handoff is internal and non-serialized; the receipt records current-task bytes, excluded ambient-note bytes, active v4 serving IDs, shadow candidate-card IDs, hard-gate rejections, catalog digest, and dormant topology revision without raw task text. Receipt failure or missing exact identity may add an operator warning but cannot change active selection, prompt bytes, usage priors, delivery, learning targets, or final output. A deterministic receipt ID makes repeated preparation overwrite the same private evidence record instead of manufacturing a second logical decision.

Virtual-manifest observation has its own default-off switch and requires the shadow-route receipt; enabling shadow routing alone still writes no manifest or delivery evidence. The observer freezes task-intent/catalog/topology/skill revisions under the exact virtual-lane digest, appends deterministic `skill-delivery.v2` evidence, and leaves active serving bytes unchanged. Runtime outcome capture records an ordinary model final as unknown until externally verified, joins delivery/outcome/episode evidence, writes one retry-idempotent terminal review, classifies bounded admitted knowledge, and can emit only checksummed reversible unapplied improvement proposals. That observer restriction prevents measurement from changing the measured serving path; it is not the mutation default. The separate current-policy synthesis path persists the proposal/decision trace and defaults to guarded autonomous apply. CLI `--propose-only` is an explicit opt-out, normal runtime jobs carry `applyAuthorized=true` and `proposeOnly=false`, and legacy jobs without those fields remain non-mutating.

Replay evidence separates receipt-derived automatic metrics from reviewed routing labels. Every frozen manifest owns all required evaluation classes through either a seed fixture or an explicit expansion-plan owner, fixture bytes and counts are checksum-bound, and `private-local` cases require an explicit load mode. Only cases marked `routingLabelsReviewed` enter precision and forbidden-rate denominators; all 53 seed turns may still contribute selection, prompt-byte, duplicate-source, class, and lane metrics.

Agent-library maintenance has two ownership levels: parallel per-virtual-session extraction claims and one serialized `agentId + libraryRevision` consolidation writer lease with heartbeat. Scheduled, startup-catch-up, and operator triggers enter the same durable job ledger and cannot bypass source admission, budgets, replay, trace, safety, or rollback policy. Foreground work wins lease contention. Candidate artifacts are written only to a staged workspace, validated before watermark advancement, and a semantically unchanged workspace completes without a model review. The current dream v1 contract remains non-mutating until the serialized writer, atomic rollback, T3 replay, and controlled T4 scheduled soak exist; after those concrete blockers close, guarded autonomous apply is the target rather than a permanent human approval queue.

Topology is a versioned routing artifact containing controlled facets, typed edges, aliases/tombstones, and materialized exact-scope views. Normal reclassification does not move canonical skill packages. An active virtual session freezes its catalog/topology revisions; candidate policy or topology is exposed only through an exact cohort overlay. Activation requires a later catalog epoch, independent candidate and rollback checksums, held-out replay, and successful downgrade/restore rehearsal. Human dream/rebaseline reports are private, marked non-indexable, and rejected from matcher, memory admission, episode synthesis, and later dream inputs.

This architecture is dormant until separately qualified. Source implementation and a cutover handoff do not by themselves authorize either shadow installation or serving activation. Shadow installation retains current serving semantics; a later activation separately changes serving policy and then promotes a reviewed catalog/topology epoch for exact cohorts. Broad guarded autonomous body and structural mutation is the target after the concrete serialized-writer, atomic-rollback, scenario-replay, and controlled-soak blockers close; it is not a permanent proposal-only or human-approval mode.
